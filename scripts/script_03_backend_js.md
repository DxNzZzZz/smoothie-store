## 1. Бекендът — Rust и Rocket

- Сървърът е написан на **Rust**, с уеб фреймуърка **Rocket**.
- Rust е системен език за програмиране, известен с изключителната си скорост и безопасна
  работа с паметта. Той улавя огромна категория грешки по време на компилация, които в езици
  като Python или JavaScript биха се появили едва по време на изпълнение.
- **Rocket** е най-популярният уеб фреймуърк за Rust. Позволява ни да дефинираме API endpoints
  с прости анотации (наречени „атрибути"), поставени директно над функцията.

### Как стартира сървърът (`main.rs`)
Когато приложението се стартира, три неща се случват по ред:
1. Създава се **пул от връзки към базата данни** — набор от многократно използваеми връзки
   към нашия SQLite файл.
2. **Миграциите се изпълняват автоматично** — всички нови `.sql` схемни файлове се прилагат
   към базата данни.
3. Rocket **монтира всички маршрути** — регистрира всеки API endpoint и всяка папка за
   статични файлове, след което започва да слуша за заявки.

## 2. API Endpoints — Договорът между фронтенда и бекенда

Всеки URL, започващ с `/api/`, е бекенд endpoint. Браузърът никога не вижда истинска страница
на тези URL-и — получава само JSON данни обратно.

Ето пълната карта на това, което бекендът може да прави:

| Метод | Endpoint                        | Какво прави                                       |
|-------|---------------------------------|---------------------------------------------------|
| GET   | `/api/home/featured`            | Връща 3 препоръчани смутита за началната страница |
| GET   | `/api/menu`                     | Връща всички негенерирани смутита с макроси       |
| GET   | `/api/menu/<id>`                | Връща едно смути и неговите съставки              |
| POST  | `/api/order`                    | Подава стандартна поръчка                         |
| GET   | `/api/custom`                   | Връща всички налични съставки за конструктора     |
| POST  | `/api/custom`                   | Подава поръчка за персонализирано смути           |
| POST  | `/api/register`                 | Създава нов потребителски акаунт                  |
| POST  | `/api/user_login`               | Влиза като потребител (задава частна бисквитка)   |
| GET   | `/api/user_logout`              | Излиза и изчиства потребителската бисквитка       |
| GET   | `/api/auth/me`                  | Казва на фронтенда кой е влязъл в момента         |
| GET   | `/api/profile`                  | Връща историята на поръчките на влезлия потребител|
| POST  | `/api/admin/login`              | Влиза като администратор                          |
| GET   | `/api/admin`                    | Връща чакащи поръчки + списък с администратори    |
| POST  | `/api/admin/order/<id>/complete`| Маркира поръчка като завършена                    |
| POST  | `/api/admin/new`                | Създава нов администратор (само супер-админ)      |
| POST  | `/api/admin/delete/<id>`        | Изтрива администратор (само супер-админ)          |

## 3. Ръкостискането — Проследяване на потребителско действие от край до край

### Пример А: Подаване на стандартна поръчка

**Стъпка 1 — Потребителят натиска „Поръчай" на формата (`order.js`)**
```javascript
const payload = {
    customer_name: document.getElementById('customer_name').value || null,
    smoothie_id: parseInt(document.getElementById('smoothie_id').value),
    size: document.getElementById('size').value
};

const res = await fetch('/api/order', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload)
});
const data = await res.json();
```
- `fetch()` изпраща данните от формата като JSON към бекенда. Страницата не се презарежда.
- Бутонът веднага се деактивира, за да се предотвратят двойни изпращания.

**Стъпка 2 — Бекендът го получава (`routes/order.rs`)**
- Rocket десериализира JSON-а в типизирана Rust структура (`OrderForm`).
- Проверява бисквитката на заявката: ако потребителят е влязъл, неговото име и ID се
  използват автоматично. Полето `customer_name` във формата става незадължително.
- `create_order()` изпълнява `INSERT` в таблицата `orders`.

**Стъпка 3 — Отговорът пътува обратно**
- Бекендът връща `{ "success": true, "message": "Поръчката е приета за Алекс!" }`.
- JavaScript чете JSON-а и показва или зелен банер за успех, или червено съобщение за грешка
  — без напускане на страницата.

### Пример Б: Конструкторът за персонализирани смутита

Това е най-сложното взаимодействие фронтенд-бекенд в проекта.

**Стъпка 1 — Страницата се зарежда, браузърът взима списъка със съставки**
```javascript
const res = await fetch('/api/custom');
const data = await res.json();   // { fruits: [...], liquids: [...] }
```
- Бекендът прави заявка към таблицата `fruits` и разделя резултатите на два списъка: плодове
  и течности.
- JavaScript изгражда целия UI за съставките динамично от тези данни — всяка карта с плъзгач,
  всеки радио бутон, всеки макро tooltip.

**Стъпка 2 — Потребителят дърпа плъзгачите (чист JavaScript, без сървър)**
- `fruitSelection` е обикновен JavaScript обект (като речник), който следи `{ fruit_id: grams }`.
- Всяко движение на плъзгача извиква `recalc()`, което:
  - Сумира всички избрани грамове плодове.
  - Изчислява колко грама течност остават за избрания размер.
  - Умножава макросите на всяка съставка по грамовете й и сумира общите стойности.
  - Прилага 10% премиум за персонализирана поръчка към цената.
  - Обновява живия панел с резюме незабавно.
- **По време на тази стъпка не се правят никакви сървърни извиквания.** Цялата математика
  се изпълнява локално в браузъра, използвайки данните за съставките, заредени в началото.

**Стъпка 3 — Потребителят изпраща поръчката**
- Изборът на съставки се сериализира в JSON и се изпраща до `POST /api/custom`.
- Бекендът валидира общото тегло на плодовете спрямо лимита за размера (напр. Малък позволява
  максимум 300 г плодове).
- Ако е валидно, бекендът изпълнява **транзакция на базата данни**: създава ред за ново
  персонализирано смути, вмъква всички редове за съставки, след което вмъква поръчката —
  и трите записа успяват или нито един от тях не се случва. Това предотвратява наполовина
  създадени поръчки в базата данни.

### Пример В: Удостоверяване — Как знаем кои сте вие

- Когато потребителят влезе, бекендът проверява bcrypt хеша на паролата и задава
  **частна бисквитка** наречена `user_id`, съдържаща ID-то му от базата данни.
- „Частна" означава, че Rocket криптира и подписва бисквитката. Потребителят не може да я
  манипулира.
- На всеки защитен endpoint Rocket проверява за тази бисквитка *преди* хендлър функцията
  изобщо да се изпълни. Ако бисквитката липсва или е невалидна, заявката автоматично се
  отхвърля.
- Фронтендът извиква `GET /api/auth/me` при зареждане на страницата, за да открие текущия
  потребител. Така навигационната лента знае дали да показва „Вход / Регистрация" или
  „Профил / Изход".

## 4. Детайли за сигурността, заслужаващи споменаване

- **Паролите** се хешират с bcrypt преди съхранение. Пароли в чист текст никога не се пазят.
- **Път за надграждане на стари акаунти**: ако по-стар акаунт е имал парола в чист текст,
  системата го открива при първото влизане, приема го веднъж и незабавно го заменя с bcrypt
  хеш. Тихо надграждане, без неудобство за потребителя.
- **Проверки за оторизация**: endpoint-ът на таблото за администратори проверява `is_superadmin`
  преди да позволи действия като създаване или изтриване на администратори. Обикновен
  администратор не може да повиши собствените си привилегии.
- **Предотвратяване на SQL инжекции**: всички заявки към базата данни използват
  параметризирани обвързвания (заместителите `?`). Потребителският вход никога не се
  конкатенира директно в SQL низ.

## Съвет: Вероятен въпрос от преподавателя

**В: „Защо избрахте Rust за бекенда вместо нещо като Node.js или Python/Flask?"**

**О:** „Rust беше съзнателно предизвикателство. Има по-стръмна крива на учене, но
компромисът е надеждност: компилаторът ви принуждава да обработите всеки възможен случай
на грешка, преди кодът изобщо да се компилира. Това означаваше по-малко изненади по
време на изпълнение. Rocket като фреймуърк отразява концепции от Flask — анотираш функция
с маршрут и метод, и просто работи — така че кривата на учене за уеб слоя беше управляема.
И тъй като SQLx проверява нашите SQL заявки по време на компилация, правописна грешка в
колонно име се улавя преди разгръщане, а не в продукция. В език като Python тази грешка
би се появила едва когато заявката действително се изпълни."
